## Findings

### P1-01 — A frozen RR member can become unavailable for an undrawn RR round

**Code:** `backend/src/AutoKorsak.Domain/TournamentEditor.cs`, `Apply(...)`, `ValidateParticipation(...)` and `PairingSchedule.GenerateRoundRobin(...)`.

**Reproduce:**
1. Create a 4-player, 3-round RR; generate **round 1 only**. This freezes `FrozenRosterIds`.
2. Edit a finalized frozen-roster member and uncheck **availability in round 2** (no pairing exists yet in round 2); save.
3. The participant editor allows the save: `ValidateParticipation` only checks roster membership / preliminary / join round, and `Apply` checks availability only against *existing pairings*.
4. Generate round 2 or generate all. The generator now fails with `generate.playerUnavailable`.

**Why it matters:** Spec §2.3 expressly says changes to a frozen RR member's availability may **not silently invalidate the frozen schedule**. The persisted edit takes a valid deterministic schedule into a state where generation is blocked.

**Expected:** Reject such an availability edit at participant-save time (with a localized explanation) or provide an explicitly specified withdrawal workflow. The current referee-decision technical-result workaround remains available and does not require marking future RR rounds unavailable. Add domain/API regression tests that edit a roster member after only the first RR round was generated.

### P2-01 — Settings system lock is not remembered after the first draw

**Code:** `TournamentEditor.IsSystemLocked` returns `Stages.Count > 1 || Rounds.Any(r => r.Pairings.Count > 0)`.

**Reproduce:** Draw/generate an RR round, then manually delete all still-unplayed generated pairings. The stage retains `FrozenRosterIds`, but `IsSystemLocked` is now false, the Settings system selector unlocks, and `UpdateSettings` can replace the first-stage system. The same semantic problem applies to a manually drawn single-stage Swiss tournament whose pairings are subsequently deleted.

**Why it matters:** Spec §2.1 expressly makes Settings read-only **once any pairing has ever been drawn**, not merely while pairings happen to exist. Changing the system this way can strand stale frozen RR metadata and bypasses the intended explicit stage-change action.

**Expected:** Persist/derive a monotonic `hasEverDrawn` condition (for RR, frozen roster already provides a sufficient signal), enforce it both in UI and backend, and test delete-all-then-settings-update plus reload. Do not equate a presently empty Pairings list with a never-drawn tournament.

### P2-02 — Unplayed RR pairings with the wrong colour orientation are silently retained

**Code:** `backend/src/AutoKorsak.Domain/PairingSchedule.cs`, `PlanRound` and `Matches`.

`Matches` considers the same unordered opponent pair compatible regardless of colours, for **both** played and unplayed pairings. Therefore manually swap the colours of an **unplayed** generated RR fixture, save, and regenerate: the generator retains that orientation, though it differs from the frozen Berger fixture and gives no replacement confirmation.

**Why it matters:** The owner required a fixed Berger colour assignment; spec §3.4 explicitly makes a **played** game with swapped colours compatible. That exception need not silently extend to unplayed pairings. The generator currently cannot restore the specified initial RR colours for unplayed games.

**Expected:** Match played games by unordered opponent pair (preserve them entirely), but match unplayed games against the **exact** Berger black/white orientation, with ordinary `generate.replaceUnplayed` confirmation before replacing a manually swapped unplayed fixture. If the product instead intends unplayed manual colour overrides to persist, explicitly amend the spec; do not infer that rule from the played-game exception.

### P2-03 — A scored bye is not treated as a recorded outcome by join defaults / stage transitions

**Code:** `Pairing.HasRecordedResult => Result != GameResult.Unset`; `TournamentEditor.RoundHasResults` and `PairingSchedule.ChangeSystem` rely on it.

A generated (or manually created) bye has `IsBye=true` and `Result=Unset`, but `StandingsCalculator` immediately awards **+1 win / +1 point**. On a round containing a bye and no result-bearing normal game:

- `RoundHasResults` returns false; a new entrant defaults to that **same** round, rather than the next.
- A stage change can treat that bye as an ordinary unplayed pairing and delete it after confirmation; it is not included in the `roundsHaveResults` barrier despite its score already being awarded.

**Why it matters:** Spec §2.2 explicitly states "Consider a result-bearing bye as a scored outcome" for joining defaults, and §1 / §4 treat a bye as a victory without a played game. The current definition of "result" is inconsistent across the generator and standings.

**Expected:** Define separately whether a round/pairing has an **awarded outcome** (including a bye) versus a recorded two-player game result. Use the awarded-outcome predicate for joining defaults. Treat credited byes consistently in stage-change safety (clarify whether already-awarded byes block transitions exactly like played games, rather than silently treating them as unplayed). Add an odd-roster RR / manual-Swiss-bye regression where the bye is the only scored outcome.

### P2-04 — Players page marks late entrants "available" in rounds before joining

**Code:** `frontend/src/pages/PlayersPage.tsx` renders each availability bullet using only `!p.notPlayingRounds.includes(r)` and a "plays" tooltip.

**Reproduce:** Add a player with `firstEligibleRound=6`. The Players list correctly displays joining round VI in its new dedicated column, but shows filled "available" bullets with "plays" tooltips for rounds I–V. The Pairings page and backend correctly recognize the player as not yet joined.

**Expected:** Derive the indicator and tooltip from `firstEligibleRound <= r && !notPlayingRounds.includes(r)`, with a distinguishable "not joined" visual/tooltip if possible. Test that pre-joining rounds cannot be mistaken for available rounds.
